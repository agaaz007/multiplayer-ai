# Native work continuation comparison

This protocol replaces the primary question used in v2. The user explicitly requires Ledger, Graphify, GBrain and Supermemory to run with their own complete supported native workflows. V2 remains a common-Git/raw-archive control, not the answer to that question. Its scores and artifacts are preserved.

## Primary question

Can another teammate recover the actual accumulated engineering or PM work and continue it correctly using the product, after the local session/worktree disappears, an external operation loses its acknowledgement, and the harness compacts context?

Each product receives its native guide, all applicable supported capture/search/graph/file/continuation features, and private persistent stores. Exact file retrieval is enabled for GBrain, full source corpus access and graph operations for Graphify, records/threads/events/artifacts/classification/snapshot resume for Ledger, and the pinned official Codex plugin, native memory/search/profile tools and original UTF8 file upload/download for Supermemory. Supermemory arbitrary binary ingestion remains an explicit unsupported adapter capability; live retrieval and scope proof are still required. Each adapter must pass actual capture and fresh-session retrieval checks before scoring. Supported native features are exercised and evidenced, not inferred from configuration. A missing capability or failed native operation remains visible. No run is called full-capability merely because an MCP server was started.

## Matched task and natural native workflows

One held-out engineering scenario and one PM scenario, seed 271, four fresh sessions A/B/C/D per product; 32 task sessions. These are exploratory scenarios, not sufficient for a broad superiority claim. Task inference stays gpt-5.6-sol, medium. Four product lanes run concurrently with both tracks serial inside each product lane, and sequential stages inside each track. Engineering stage budget is 20 minutes, PM 15 minutes. Native automatic capture receives up to 300 seconds, measured separately. Newly charged provider calls consume the existing shared $30 budget, which is not reset. Subscription inference stays separately reported.

Only the identical initial project scaffold and current stage's new input are copied by the controller. Prior source documents, reports, scripts, code and derived state remain in product stores. No controller copies predecessor code, raw archives, handoff summaries, Git history or private transcript into a successor. Product-supported storage/indexing may ingest actual workspace bytes; it cannot create semantic handoff content. Agent-native use of Git snapshots, attachments, pages, graphs, evidence stores and resume packs is allowed and attributed to its actual mechanism.

This is a local-workspace-loss simulation on one machine. Native stores remain available; it does not establish multi-machine transport or tenant ACL security. Product-specific representations and normal documented save/import workflows are allowed. A shared output contract gives reviewers inspectable work products; it does not constrain native memory representation.

## Four stages and two stress boundaries

- A produces original work, source-backed rationale, open questions and executable artifacts.
- B recovers A, applies the next change/correction, and leaves a planned external operation under an opaque generated key. After delivering work and persisting its intent, it submits once to a synthetic non-idempotent supplier. The supplier commits, withholds acknowledgement, and signals the controller to kill the task process after one second. The exact trigger, process kill, native capture and loss window are retained. No agent can write a retrospective handoff after interruption.
- C recovers original and corrected work plus the pending key, looks up the actual supplier receipt before any repeat, and extends the work. A configured 12,000-token body-after-prefix compaction threshold applies equally to all C sessions. Native rollout compaction events are required to claim compaction occurred; absence is not_evaluated for that stress. Fresh sessions alone are not compaction. No filler is inserted or primary stage retried merely to get an event.
- D recovers accumulated work and applies a scoped correction while rejecting an unapproved proposal. Earlier valid evidence, decisions and operation receipts must remain inspectable.

PM work compares product investments, preserves provisional and corrected experiment evidence, makes a feasible sprint plan, and responds to a reliability breach. Engineering work extends Dispatch's ownership/idempotency API through execution, batches and cancellation. The synthetic supplier operation is a separate real state transition in the test fixture, with a private event oracle; no real customer or payment is contacted.

## Observable outcomes

Before modifying recovered predecessor files, a successor calls `recover_handoff`. This only freezes actual workspace bytes and agent-supplied source references. It does not provide expected hashes or restore anything. Exact artifact fidelity and state recovery are checked against actual immutable predecessor artifacts. Missing producer output is a producer failure and dependent recovery is not_evaluated; it cannot be silently scored as successful recovery. Preserve attempted failures and missing receipts.

Report separately: native feature admission/usage; original-artifact recovery; current/proposed/superseded state and unfinished questions; interrupted-operation reconciliation/no duplicate effects; final engineering correctness; PM factual and decision quality; delivery, recovery, native capture and total effort. Trace attribution requires a producer, native retrieval and actual contribution. Citation-only claims do not establish use. Native acceptance metadata does not establish human approval.

The handoff snapshot is the actual final worktree before automatic post-stage capture. It remains controller-private and is never a transport source. Task delivery is independently frozen, so later native bookkeeping cannot silently replace the scored answer. Recovery and task quality are distinct: exact recovery of a flawed recommendation is faithful recovery, not a good decision.

Engineering reuses the uniformly corrected v2 public behavioral scorer, with all original checks retained. PM reviewers receive the stage-visible source evidence and actual retrieved predecessor material with neutralized product identities, so legitimate inherited state is assessable. At least two independent model reviews and an adjudicator for disagreement remain separate from deterministic evidence validation. No pooled engineering/PM overall score.

## Admission and immutable audit

Freeze scenario bytes, native versions/local modifications, adapters, guides, inference settings, budgets, capture schedule, graders and launch configuration before scored tasks. Validate every successor's kernel-denied access to predecessor worktrees, private pack and controller artifacts. Actual native file/save/restore, complete capture/index state, and key tool availability must be demonstrated. Deterministic mocked transport checks do not establish live readiness.

Keep unscored setup/development probes separate. Fix harness problems before scoring; if a scored failure is caused by infrastructure, retain the original attempt and describe any new entire comparison explicitly. Do not repair one product's memories, change its time budget, or select a better result after seeing scores. Real product capture failures are outcomes.

Codex compaction configuration is documented at https://learn.chatgpt.com/docs/config-file/config-reference ; the actual recorded event remains the evidence of execution.

## Record-use admission and limits of attribution

Ledger admission requires an unscored A→B→C native trace chain: A creates a work record; B proposes an evidence-backed correction on that record and successfully confirms it; a distinct C session retrieves that confirmed version; C then uses the opaque pending key from that native state to look up the supplier's actual receipt and includes it in its immutable delivery. `mechanisms.py` binds requests and responses, session IDs, source hashes, record/update IDs, state versions, temporal order, the provider oracle and delivered bytes. The readiness source witness binds the accepted B source/value to the corrected record text. The matrix recomputes the audit from its hashed originals. Classifier-enabled, PROPOSED, stale state, failed acceptance, citations and controller-authored success receipts cannot pass.

All four products receive the same readiness task in `readiness.py` and may use their own native representation. Ledger's protocol is not imposed on other products. The primary grader reports trace-supported use where observed; complex primary correction semantics still need independent source review. Use does not establish that records caused better results or that snapshots/retrieval made no contribution. No ablation or broad superiority conclusion is inferred from the native comparison.

## Shared disk admission and intervention disclosure

Every launch has explicit retained-output and peak-working/capture estimates. `disk_budget.py` atomically reserves both tracks' retained output, the maximum serial-track peak per product lane, and shared overhead plus margin, across all four lanes. Other controllers' active and crashed-owner commitments remain counted. There is no automatic stale-PID expiry. Runtime guards stop owned processes when another lane's reserved headroom is threatened. These are conservative commitments, not hard filesystem quotas; unrelated processes can still consume disk.

The prepared primary estimate is 7.5 GiB: eight times 512 MiB retained, four times 256 MiB peak, 512 MiB shared overhead and 2 GiB margin. It derives from incomplete prior readiness observations and must be checked against a completed four-product readiness run before the primary freeze. Do not lower it merely to fit available storage. The readiness estimate is 5.5 GiB. Existing installed dependencies are already reflected in measured free space.

Freeze `known-issues.json` with each scored launch. It preserves the short-file evidence failure and Supermemory's file-support boundary. Before any intervention, run `integrity.py` with the sequence root, actor, action, reason and affected paths. Freeze checks run at stage boundaries and after task execution/capture; recorded interventions stop that attempt and remain in the report. Manual interventions cannot be inferred reliably from logs alone, so the operator must record them. Any product fix or adapter change belongs before freeze and requires fresh readiness. No repairs or backfills during scored tasks.
